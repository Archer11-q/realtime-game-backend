# 质量、测试与可观测性

> 状态：已确认（2026-09-14），**2026-10-02 按 [ADR-0003](adr/0003-scope-reduction.md)
> 移除消息队列相关的测试与指标要求。**

## 1. 质量原则

- 正确性优先于吞吐量。
- 已知失败必须可检测、可解释和可恢复。
- 没有基线不做性能结论。
- 没有原始记录不对外给出性能数字。
- 测试必须验证行为和不变量，而不是只验证函数被调用。
- 先定位瓶颈，再用最小改动优化，最后做回归验证。

## 2. 测试分层

### 单元测试

范围：

- 状态机合法迁移。
- 匹配规则、队列和取消。
- 幂等键和重复请求。
- 数据序列化和协议校验。
- 连接会话状态转换。

要求：

- 每个核心模块有独立测试目标。
- 失败用例覆盖空值、重复、越界、超时和非法状态。
- 测试不依赖真实网络时使用受控替身。

### 集成测试

范围：

- Gateway -> Match -> Room 的 brpc 调用。
- Redis/MySQL 存储和恢复。
- 对局结果的同步幂等写入与重复写入。
- SSE 推送链路：订阅数、推送次数、被清理的失效连接。

要求：

- 使用 Docker Compose 启动真实依赖。
- 每个测试有独立数据命名空间或清理策略。
- 测试结束不能遗留容器、端口和临时数据。

### 端到端测试

核心流程：

1. 两个玩家登录。
2. 双方进入匹配。
3. 匹配成功并进入同一房间。
4. 开始游戏并发送输入。
5. 一方断线并在宽限期内重连。
6. 对局结束并由 Room/Battle 同步幂等写入对局结果。
7. 查询对局结果。

### 长稳和故障测试

- 持续运行连接建立、断开和重连。
- 服务进程重启。
- Redis 或 MySQL 暂时不可用。
- 业务进程崩溃（`kill -9`）与重启恢复。
- 连接风暴和突发请求。

## 3. Sanitizer 和静态检查

| 工具 | 用途 | 触发时机 |
|---|---|---|
| ASan | 越界、UAF、泄漏 | 单元测试、内存相关改动、合并前 |
| TSan | 数据竞争和锁问题 | 并发模块、连接和房间状态改动 |
| UBSan | 未定义行为 | 核心模块合并前 |

## 4. 可观测性三要素

### 结构化日志

日志必须包含：

- 时间、级别、服务名、版本和实例 ID。
- `request_id`、`session_id`、`player_id`、`room_id`、`match_id`（存在时）。
- 事件名称、结果、耗时和错误码。
- 不包含 Token、密码、私钥和完整敏感载荷。

### 指标

首批指标：

- 当前连接数、连接建立/断开速率。
- HTTP/SSE 请求数、QPS 和错误率。
- RPC 调用数、延迟直方图和超时。
- 匹配人数、等待时长和匹配成功率。
- 活跃房间数、房间创建/销毁速率。
- 重连次数、成功率和 Session 过期数。
- 推送补发：补发帧数与 `stream.reset` 次数（**按原因分开**，TASK-017）。
  「窗口外」说明客户端落后得比缓冲还多，「id 超前」说明客户端与服务端对不上，
  而「首次订阅」是正常路径——合成一个数字就看不出这次 reset 是不是问题。
  当前实现已经暴露了这两个计数（`StreamHub::BackfilledFrameCount` /
  `ResetEventCount`），接入 Prometheus 属 Phase 3。
- Redis/MySQL 调用延迟和失败率。
- 进程 CPU、内存、FD 和线程数。

### 链路追踪

**已实现（TASK-018 ~ TASK-021）**：不引入 OpenTelemetry SDK、也不部署 OTLP
collector（这是项目所有者 2026-10-02 确认的决策）。做法是**共用同一个 id 写进三个
服务的结构化日志**，满足"任一错误可以定位到服务、请求、会话或房间"这条退出标准；
真正的 span 导出留到需要时再评估（它需要额外的 C++ 依赖与 collector）。

约定：

- **id 就是 `request_id`**，经 proto 的既有字段在 Gateway → Match → Room 之间透传，
  **不新增契约字段**。Gateway 的每个 HTTP 响应都会留下一条
  `event=request_done`（含 `op=`、`status=`、`trace=`），因此"每个请求都可检索"不依赖
  谁来记得加日志。
- **配对这类异步环节取"该组队首玩家"的 request_id**。配对可能由第二个玩家入队触发，
  也可能由轮询触发的惰性重试触发；取队首才与"谁触发"无关，因此确定、可复现。
- **没有 id 时不编造**：`request_id` 为空的行不输出 `trace=` 字段，也不生成伪 id。
  （这一条是有代价的：这类请求只能靠 `op=` 与时间定位。宁可少一个字段，也不要一个
  在别处查不到的假 id。）
- **不做跨服务的时序排序断言**：三个进程各自取系统时钟，毫秒级先后会受调度影响，
  那不是缺陷。可判据是"两边有同一个 trace"，即因果关系，而不是时钟先后。
  单个服务内部仍要求同一 trace 的时间戳单调不减。

优先追踪的五条路径与它们的落点：

| 路径 | 跨服务环节 |
|---|---|
| 登录 | Gateway `request_done(op=login)` |
| 进入匹配 | Gateway `match_enqueue_ok` → Match `match_enqueued` → Room `room_created` |
| 创建/加入房间 | Gateway `request_done(op=join_room)` → Room `room_joined` |
| 断线重连 | Gateway `subscribe_ready` → Room `presence_reported`（在线/离线两次） |
| 对局结果 | Gateway `request_done(op=get_match_result)` → Room `match_result_queried` |

对局结果的**写入**发生在 Room 的推进线程上，没有请求上下文，因此它用 `match_id`
关联（见 `room_manager.cpp` 的 `result_persist_failed`）——这是有意的不对称：
"这一局的结果写失败了吗"问的是对局，不是某一次 HTTP 请求。

验收命令：`bash scripts/verify-trace.sh`（也可经 `scripts/verify-all.sh` 一起跑）。
它逐条断言上表五行，并检查"未带 `request_id` 时不编造 trace"与"结构化行没有被
字段值断行"两条不变量。

> **不使用消息队列**，因此没有消费位点、Lag、死信和重复消费相关的测试与指标，
> 见 [ADR-0003](adr/0003-scope-reduction.md)。

## 5. SLO 和容量目标

初始目标见项目章程。调整目标必须满足：

- 有正式 ADR。
- 说明原目标无法达到的技术原因。
- 不掩盖真实回归。
- 不修改历史压测结果。

每次压测报告至少包含：

- 代码版本和构建类型。
- 机器 CPU、内存和内核版本。
- 服务实例数、连接数和房间数。
- 测试持续时间、think time 和请求分布。
- QPS、p50、p95、p99、最大值和错误率。
- CPU、内存、FD、网络和中间件指标。
- 原始日志、脚本和必要的火焰图。
- 已知限制和不能代表的生产条件。

## 6. 性能优化流程

```text
固定环境
  -> 建立基线
  -> 复现瓶颈
  -> 收集证据
  -> 提出一个假设
  -> 做最小改动
  -> 回归测试
  -> 对比数据
  -> 保留或回退
```

禁止：

- 没有基线就优化。
- 同时修改多个变量后归因。
- 只展示优化后数据。
- 通过减少请求、关闭校验或改变测试负载制造“提升”。
- 用平均延迟代替尾延迟。

## 7. 发布门禁

每次阶段发布前必须：

- 全量测试通过。
- ASan/TSan 按影响范围通过。
- 数据库迁移可重复执行并说明回退。
- 配置和依赖版本固定。
- README 和 Runbook 可复现。
- 关键指标存在且有面板。
- 已知问题已记录，不隐藏。
- 演示脚本实际运行成功。

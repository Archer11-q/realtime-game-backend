## 2. 仍需确认

### D-002：登录方案

第一版建议使用测试账号或固定 Token，不实现完整注册系统。

需要确认：

- 是否使用简单 JWT 风格 Token。
- 是否将账号密码存入 MySQL。
- 是否需要刷新 Token，还是只实现短期会话。

### D-003：对局同步方式

当前演示目标是“最小实时对战”，需要选择：

- 状态同步：服务端广播状态快照。
- 帧同步：服务端收集输入并广播帧。
- 混合：房间广播输入，客户端展示预测状态。

建议第一版使用最小状态同步或简化帧同步，优先保证连接、房间和重连链路。

### D-004：Kafka 的进入时机

Kafka 已用于目标架构，但不应在第一周启动。

建议触发条件：

- 结算需要从主请求链路解耦。
- 需要消费位点、重试和回放。
- 需要异步统计或排行榜更新。

### D-005：etcd 的进入时机

建议仅在至少有两个 Gateway/Match 实例，并且出现服务发现或故障恢复问题时引入。

## 3. 风险清单

| 风险 | 触发信号 | 处理方式 |
|---|---|---|
| 项目范围膨胀 | 任务频繁加入新服务和新中间件 | 回到当前阶段的退出标准 |
| 前端耗时过多 | 页面功能超过演示范围 | 限制为登录、匹配、房间、Canvas 和结果 |
| AI 代码冲突 | 多个模型同时改同一文件 | 只允许 Claude 写入代码 |
| 依赖版本漂移 | 不同机器构建结果不同 | 固定版本和锁文件 |
| 过早分布式 | 本地调试成本急剧上升 | 先单机闭环，按证据拆分 |
| 性能数据不可信 | 没有原始脚本和环境记录 | 压测结果不作为正式结论 |
| 文档和实现分裂 | 代码行为与 ADR 不一致 | 变更先更新文档，再改代码 |

## 4. 决策变更流程

1. 记录当前问题和新证据。
2. 给出至少两个可选方案。
3. 分析正确性、复杂度、性能、成本和学习价值。
4. 项目所有者确认。
5. 写 ADR。
6. 更新架构、路线图和任务文档。
7. 再开始相关实现。

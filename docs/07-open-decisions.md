## 2. 已关闭的开放决策（原「仍需确认」）

以下两项在 2026-10-02 由项目所有者确认为**固定结论**，不再是开放问题。
完整理由、替代方案与连带影响见 [ADR-0003](adr/0003-scope-reduction.md)。

### D-004：Kafka 的进入时机 —— 已关闭：**不引入**

原记录为"Kafka 已用于目标架构，但不应在第一周启动"，并列了三个建议触发条件。
现在的结论是：**本项目不实现 Kafka 或任何消息队列**。

理由：三个触发条件在本项目内都不会真实出现——对局结果只需一次同步幂等写入，
不需要从主链路解耦；不需要消费位点和重放；不做异步统计和排行榜。

### D-005：etcd 的进入时机 —— 已关闭：**不引入**

原记录为"仅在至少有两个 Gateway/Match 实例，并且出现服务发现或故障恢复问题时引入"。
现在的结论是：项目**不做多实例部署**，该触发条件在本项目内永远不会满足，
etcd 及任何服务注册、发现、租约机制列入非目标。

**注意**：这两项已不是"暂未满足条件"，而是"不做"。任何引入都必须先撤销或修改
ADR-0003，不能以"现在满足条件了"为理由直接实现。

## 3. 风险清单

| 风险 | 触发信号 | 处理方式 |
|---|---|---|
| 项目范围膨胀 | 任务频繁加入新服务和新中间件 | 回到当前阶段的退出标准 |
| 前端耗时过多 | 页面功能超过演示范围 | 限制为登录、匹配、房间、Canvas 和结果 |
| AI 代码冲突 | 多个协作者同时改同一文件 | 只允许单一执行者持有写入权 |
| 依赖版本漂移 | 不同机器构建结果不同 | 固定版本和锁文件 |
| 过早分布式 | 本地调试成本急剧上升 | 服务只拆三个且不做多实例（ADR-0003） |
| 性能数据不可信 | 没有原始脚本和环境记录 | 压测结果不作为正式结论 |
| 文档和实现分裂 | 代码行为与 ADR 不一致 | 变更先更新文档，再改代码 |

## 4. 决策变更流程

1. 记录当前问题和新证据。
2. 给出至少两个可选方案。
3. 分析正确性、复杂度、性能、成本和学习价值。
4. 项目所有者确认。
5. 写 ADR。
6. 更新架构、路线图和任务文档。
7. 再开始相关实现。

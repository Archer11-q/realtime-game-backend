# 开发协作流程

> 状态：已确认（2026-09-14）

## 1. 角色分工

| 角色 | 主要职责 | 禁止事项 |
|---|---|---|
| 项目所有者 | 确认需求、审阅代码、运行验收、合并 PR | 不把重要决策只留在聊天中 |
| Claude | 主要代码开发、测试、调试、技术文档 | 不扩大范围，不跳过确认和测试 |
| 豆包 | Git、WSL、Docker、CLion、命令和操作解释 | 不决定架构，不直接修改仓库 |
| DeepSeek | 概念解释、报错分析、局部代码审查 | 不替代主开发，不并发编辑代码 |
| 协调 AI | 任务拆分、验收标准、独立审查 | 不与主开发同时修改同一分支 |

同一时间只能有一个 AI 拥有代码写入权。

## 2. 单一真相来源

信息优先级从高到低：

1. 项目所有者最新明确确认。
2. 已合并代码与自动化测试结果。
3. `CLAUDE.md`、ADR 和已确认设计文档。
4. `TASKS.md` 中的当前任务。
5. `devlog.md` 中已记录的事实。
6. 聊天中的临时讨论。

聊天答案与仓库文档冲突时，以仓库文档为准；若二者都不清楚，停止实现并请求确认。

## 3. 任务生命周期

```text
提出任务
  -> 定义问题与验收标准
  -> 检查架构和 ADR
  -> 写入 TASKS.md
  -> 项目所有者确认
  -> Claude 输出实施计划
  -> 创建分支
  -> 编码和测试
  -> 更新文档/devlog
  -> 提交 PR
  -> CI 检查
  -> 项目所有者验收
  -> 合并
```

任务未写入 `TASKS.md` 前，不允许直接进入大规模编码。

## 4. 任务单模板

```markdown
### TASK-XXX：任务名称

- 状态：待确认 / 进行中 / 待验收 / 已完成 / 阻塞
- 背景问题：
- 本次目标：
- 范围：
- 非范围：
- 相关 ADR：
- 涉及目录：
- 接口变化：
- 数据变化：
- 失败场景：
- 验收命令：
- 测试要求：
- 回退方式：
- 负责人：
```

## 5. Claude 启动提示词

```text
先不要修改代码。
请阅读 CLAUDE.md、docs/README.md、docs/00-charter.md、
docs/01-architecture.md、docs/02-roadmap.md、当前 TASK 和相关 ADR。

输出：
1. 你对任务的理解
2. 本次包含和非范围
3. 涉及模块与文件
4. 实施步骤
5. 失败场景与兼容性风险
6. 测试和验收方案
7. 需要项目所有者确认的问题

等待确认后再编码。
```

## 6. Claude 实施提示词

```text
实现 TASK-XXX。

约束：
- 只修改任务允许的范围。
- 不增加未确认功能。
- 不引入新依赖，除非先给 ADR 建议并等待确认。
- 完成后运行任务规定的构建和测试。
- 更新文档和 docs/devlog.md。
- 输出修改文件、设计理由、测试结果、风险和下一步。
```

## 7. 豆包使用场景

适合询问：

- WSL、CLion Toolchain 和 CMake 命令。
- Git clone、branch、commit、pull、push、rebase 和冲突处理。
- Docker、Compose、端口和卷相关操作。
- 环境安装、版本检查、常见命令排错。

提问模板：

```text
我的环境是 WSL2 Ubuntu 26.04 LTS，当前目录是 ...，当前分支是 ...
我想完成 ...。
请按顺序给出命令，解释每条命令的作用、适用目录、预期输出、
可能失败的原因和不破坏数据的回退方式。
不要假设我已经完成前置步骤。
```

涉及删除、重置、强制推送等高风险管理命令时，必须先向项目所有者解释影响，
不能直接执行。

## 8. DeepSeek 使用场景

适合询问：

- C++、Linux、网络、数据库和分布式概念。
- 编译错误、运行错误和测试失败的解释。
- 一段代码的调用链、潜在 Bug 和替代实现。
- 概念讲解、原理推导和追问练习。

提问模板：

```text
这是我的项目上下文和相关代码片段：...
这是我的目标：...
这是报错或疑问：...

请先解释根因和涉及概念，再给出最小修复方案、替代方案和测试建议。
不要假设未提供的架构，不要直接重写整个模块。
```

## 9. 分支和提交

- `main` 始终保持可构建、可测试。
- 功能分支使用 `feat/<task-id>-<short-name>`。
- 修复分支使用 `fix/<task-id>-<short-name>`。
- 文档分支使用 `docs/<task-id>-<short-name>`。
- 提交信息使用 `feat: ...`、`fix: ...`、`test: ...`、`docs: ...`、
  `build: ...` 或 `chore: ...`。
- 一个 PR 只解决一个问题。
- 不提交构建目录、IDE 配置、密钥、日志和个人路径。

## 10. 代码审查清单

审阅者至少检查：

- 是否解决任务定义的问题，而不是扩大范围。
- 是否违反服务边界和数据所有权。
- 是否处理错误、超时、重复请求和并发。
- 是否有可能的空指针、悬空引用、泄漏和数据竞争。
- 是否有测试，测试是否能失败并捕获回归。
- 是否改变接口、数据库 schema 或配置。
- 是否更新 ADR、接口文档和 devlog。
- 是否存在无法解释的性能或资源开销。

## 11. PR 合并条件

- 任务范围明确。
- 构建、测试和静态检查通过。
- 项目所有者已审阅关键 Diff。
- 文档、迁移和配置同步更新。
- 没有未解释的警告和遗留文件。
- 需要 Sanitizer 的任务已运行对应检查。

## 12. AI 协作纪律

- 不让多个 AI 同时编辑同一仓库。
- 不把完整密钥、Token、私钥或真实用户数据发给任何 AI。
- 不要求 AI 编造项目经历、用户量、QPS 或线上结果。
- 外部 AI 的结论必须经过代码、测试或官方文档验证。
- 每个阶段的结论必须写回仓库。
- 发现 AI 建议与设计冲突时，先报告冲突，不直接实现。

# ADR-0002：Gateway 临时直接读取玩家档案

- 状态：已接受
- 日期：2026-09-17
- 决策者：项目所有者
- 关联任务：TASK-006

## 背景

`docs/01-architecture.md` 的数据所有权表规定「玩家档案和战绩」的所有者是
**Player/State 服务**，存储为 MySQL，并明确「任何模块不得绕过所有者直接修改数据」。

TASK-006 需要建立 `players` 表并让玩家档案具备真实读写，以验证数据模型是否合理
（只建空表无法验证这一点）。但 Phase 1 的范围清单（`docs/02-roadmap.md` 第 4 节）
包含 Match、Room/Battle、WebSocket 与 Vue 演示，**不包含 Player/State 服务**。

因此出现一个现实矛盾：表需要被读，而它的所有者服务在 Phase 1 不存在。

## 决策

**在 Phase 1 期间，由 Gateway 直接读取 `players` 表**，作为明确的**临时安排**：

- 读取路径封装在 `PlayerReader` 接口之后，Gateway 只依赖接口，不直接拼 SQL。
- 本人负责范围仅限**读取**：Gateway **不写** `players` 表。测试数据由迁移脚本
  （`migrations/004_seed_test_players.sql`）写入。
- 本 ADR 是「不得绕过所有者」这条边界规则的**唯一例外**，且带有明确退出条件。
- 账号密码仍保留在代码中作为测试数据，**不进入数据库**（依据 D-002）。

## 备选方案

### 方案 B：在 Phase 1 就实现 Player/State 服务

优点：

- 完全符合文档的服务边界，不存在例外。
- Gateway 通过 brpc 调用，边界清晰。

缺点：

- Phase 1 范围因此增加一个服务（proto、服务实现、测试、部署配置）。
- 该服务在 Phase 1 只有「按账号查档案」一个能力，其余职责（会话映射、战绩查询、
  排行榜）要等到 Phase 2/5 才有真实需求，属于提前实现。
- 会明显拖慢 Phase 1 的核心目标（双客户端完成最小对战）。

结论：不作为当前选择，但保留为正式归属（见「替代关系」）。

### 方案 C：修改所有权表，声明 Gateway 是第一版的玩家档案所有者

优点：

- 不需要例外，文档与实现一致。

缺点：

- 所有权是长期约定，为了一轮任务的便利而改动，后续要再改回来，属于反复变更。
- 玩家档案在 Phase 2 明确需要由 Player/Settlement 承接（战绩写入），届时仍要迁移。

结论：不采用。用带退出条件的临时例外比反复修改长期约定更清晰。

### 方案 D：只建表，不实现读取路径

优点：

- 不引入任何例外。

缺点：

- 空表无法验证数据模型是否合理，达不到 TASK-006 的目标。
- 与项目所有者选择的方案冲突。

结论：不采用。

## 后果

### 正面

- Phase 1 能用最小的改动让玩家档案具备真实读写，验证表结构。
- 例外被显式记录并有退出条件，不会沉淀为「无人知道为什么这样」的遗留设计。
- `PlayerReader` 接口保证了替换成本可控：迁到 Player/State 时只换实现。

### 负面

- **存在一处已知的边界违反**，必须靠本 ADR 与文档注记防止被误认为正式设计。
- Gateway 因此多了一个 MySQL 依赖（`libmariadb`）。
- 若 Player/State 迟迟不落地，这个临时安排会持续存在，需要在 Phase 2 主动检查。

## 验证方式

- `players` 表由迁移脚本创建，含 3 行测试玩家数据。
- `bash scripts/verify-login.sh` 全项通过，且登录路径确实从数据库读取档案：
  停止 MySQL 后登录返回 503 `player_store_unavailable`，恢复后无需重启即可登录。
- 全仓库确认 Gateway 未对 `players` 执行任何写操作。

## 替代关系

**本 ADR 在 Player/State 服务落地时标记为「已替代」。**

退出条件（满足任一即需处理）：

1. Player/State 服务在 Phase 2 实现并可通过 brpc 查询玩家档案；
2. 系统出现第二个需要读取玩家档案的服务（此时直接读取会扩散，必须收敛）。

处理方式：新增 ADR 记录迁移，将本 ADR 状态改为「已替代」，
并把 `docs/01-architecture.md` 的所有权表注记一并更新。

# ADR-0003：范围裁剪——取消多实例、Kafka、etcd 与独立玩家/结算服务

- 状态：已接受
- 日期：2026-10-02
- 决策者：项目所有者
- 关联任务：TASK-012
- 部分替代：[ADR-0001](0001-initial-platform-and-stack.md)（技术栈中的 Kafka 与 etcd 两项）、
  [ADR-0002](0002-gateway-temporary-player-ownership.md)（把"临时例外"改为正式归属）

## 背景

`docs/02-roadmap.md` 原定 Phase 4（多实例和故障治理，引入 etcd）、Phase 5（事件闭环
和回放，引入 Kafka 与 Settlement Worker），并计划实现 Player/State 独立服务。

在 2026-10-02 的范围复盘中，项目所有者指出这组计划存在三个问题：

1. **组件与项目成果不匹配。** 项目的可验证产出是"有状态实时服务在故障下的行为"，
   而 etcd、Kafka 属于基础设施编排能力。加入它们会让项目变成"组件堆叠"，而不是
   "问题被验证解决"。
2. **没有真实触发条件。** Kafka 的消费者（Settlement）和 etcd 的消费者（多实例
   服务发现）在当前架构里都不存在。此时引入等于先建管道再找水源，违反本项目
   `CLAUDE.md` 第 6 条"每一次迭代必须对应真实问题或验收标准"。
3. **成本挤占。** 剩余可用时间不足以在完成 Phase 1-3 的同时，再从零学习并正确
   使用两个分布式中间件。

同时出现一个连带问题：`players` 表的正式所有者（Player/State）和
`match_results` 表的正式所有者（Settlement）如果都不实现，这两张表会失去归属。

## 决策

### 1. 明确列入非目标（**不实现**，不是"延后"）

以下内容在项目的可预见范围内**不再实现**。任何 AI 或协作者**不得**为其创建目录、
proto、服务、Compose 服务或迁移脚本：

| 非目标 | 原计划位置 |
|---|---|
| Kafka 及任何消息队列 | 原 Phase 5 |
| 领域事件、事件回放、异步结算 Worker | 原 Phase 5 |
| etcd 及任何服务注册/发现/租约机制 | 原 Phase 4 |
| 多实例部署与水平扩展 | 原 Phase 4 |
| Kubernetes / k3s / 任何容器编排 | 原 Phase 4 及 ADR-0001 |
| Settlement 服务（独立进程） | 原 Phase 5 |
| Player/State 服务（独立进程） | 原 Phase 2 |
| 排行榜 | 原 Phase 2 |
| 匹配分差放宽 / MMR / 评分体系 | 原 Phase 1 之后 |

### 2. 服务集合固定为三个

| 服务 | 职责 | 数据所有权 |
|---|---|---|
| Gateway | HTTP/WebSocket、鉴权、路由、心跳、限流、会话 | `players`（只读） |
| Match | 匹配队列、FIFO 两人配对、取消、房间分配 | 匹配队列（进程内存） |
| Room/Battle | 房间生命周期、权威状态、快照、对局同步 | 房间状态、`match_results` |

### 3. 数据所有权调整

- **`players` 表的所有者改为 Gateway**。原 [ADR-0002](0002-gateway-temporary-player-ownership.md)
  把它记为"带退出条件的临时例外"；本 ADR 取消该退出条件，使其成为项目范围内的
  正式归属。实现上 `PlayerReader` 接口保留不变。
- **`match_results` 表的所有者改为 Room/Battle Service**。对局结束时由 Room
  **同步、幂等**写入（以 `match_id` 为幂等业务键），不经过任何消息队列。
  Settlement 服务不实现。
- 两张表的迁移脚本（`migrations/002`、`003`）保持不变，仅更新表内注释。

### 4. 产品目标调整

`docs/00-charter.md` 的功能目标与本节保持一致：

- **保留**：登录、匹配、进入房间、最小实时对战、断线重连与宽限期恢复、
  对局结果的写入与查询。
- **移出**：排行榜、领域事件重放、异步结算。

### 5. 路线图重排

原 Phase 4 与 Phase 5 取消，原 Phase 6（工程收口）的可靠性验证内容提前：

| 阶段 | 内容 |
|---|---|
| Phase 0（已完成） | 基线和设计 |
| Phase 1（进行中） | 最小业务闭环 |
| Phase 2 | 持久化和恢复 |
| Phase 3 | 可观测性和容量基线 |
| Phase 4 | 故障注入与可靠性验证 |
| Phase 5 | 工程收口 |

**Phase 4 的验证对象变为**：进程崩溃与恢复、断线重连、依赖不可用降级、
优雅退出与排空、连接风暴。这些都是单实例内可以真实验证的故障，
不需要 etcd 或 Kafka。

## 备选方案

### 方案 B：保留 Phase 4/5，只推迟到时间允许时再做

优点：

- 不改变原架构蓝图，文档改动最小。

缺点：

- "推迟"在文档里没有约束力——后续 AI 读到 Phase 4/5 仍会按计划实现。
- 项目所有者明确指出这组内容与目标岗位的匹配度低，推迟等于长期悬空。

结论：不采用。范围裁剪必须写成"不实现"，否则不生效。

### 方案 C：保留 Settlement 作为独立服务，只用 brpc 同步调用，不接 Kafka

优点：

- 服务边界更"正统"，结算逻辑不侵入 Room。

缺点：

- 服务数从 3 变 4，但对局结算本身只有一次幂等写入，独立进程不带来任何
  隔离或扩展收益。
- 增加一个 proto、一个进程入口、一套测试与部署配置，成本与收益不成比例。

结论：不采用。结算作为 Room 结束流程的一部分同步完成，更简单也更少故障面。

### 方案 D：完全删除 `match_results` 表与结算功能

优点：

- 范围最小，不留悬空表。

缺点：

- 迁移脚本已经交付并应用，删除属于破坏性变更，违背"迁移只追加"的约定。
- 幂等写入是本项目少数能完整讲清"重复请求安全"的链路，删掉会损失一个
  有验证价值的场景。

结论：不采用。保留表定义，改由 Room 写入。

## 后果

### 正面

- 项目范围收敛到"三个服务 + 两个数据组件"，剩余时间可以用于深度而非广度。
- 每个保留阶段都有可在单机真实验证的退出标准，不依赖外部基础设施。
- 消除了两处"表没有所有者"的悬空状态。
- "为什么不做 Kafka/etcd"本身成为可讲的工程判断，而非缺失。

### 负面

- **简历与项目描述中不能再出现 Kafka、etcd、服务发现、消息队列等关键词。**
  README 与项目定位必须同步修改，否则文档与事实不符。
- 项目不再覆盖分布式协调与事件驱动两类能力，覆盖面变窄。这是有意选择。
- 若日后确实需要多实例，需要重新走 ADR 流程，不能直接恢复原 Phase 4。

## 验证方式

- 全仓库检索 `Kafka`、`etcd`、`Settlement`、`Player/State`、`多实例`，确认
  剩余出现处均为"非目标"说明或历史记录，不存在实现指引。
- `docs/02-roadmap.md` 的阶段表与本文第 5 节一致。
- `docs/01-architecture.md` 的服务列表与数据所有权表与本文第 2、3 节一致。
- `deploy/compose/.env.example` 不再包含 `KAFKA_BROKERS`、`ETCD_ENDPOINTS`。
- 本 ADR 生效后，任何试图新增上述非目标组件的任务单都必须先撤销本 ADR。

## 替代关系

- **部分替代 ADR-0001**：ADR-0001 的决策列表中"Kafka 用于后续异步和回放阶段"
  与"etcd 用于后续多实例和服务发现阶段"两项由本 ADR 取代为"不实现"，
  其余技术栈选择维持有效。
- **取代 ADR-0002 的退出条件**：ADR-0002 的临时例外转为正式归属，其
  "替代关系"一节由本 ADR 取代。

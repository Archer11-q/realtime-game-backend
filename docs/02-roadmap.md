## 1. 迭代原则

项目按“正确 -> 可恢复 -> 可观测 -> 可验证”推进。

每一阶段必须回答：

1. 当前存在什么问题？
2. 为什么现在必须解决？
3. 不解决会影响哪个功能、指标或故障场景？
4. 最小改动是什么？
5. 如何证明问题被解决？
6. 哪些能力明确留到后续，不提前实现？

版本号只记录已经交付的结果，不驱动开发。压测只用于建立基线和发现瓶颈，
不是自动进入优化的理由。

**范围裁剪后的定位**：项目的价值在于「有状态实时服务在故障下的行为可被实测」，
而不是「接入了多少种中间件」。因此阶段划分以**可独立验证的故障场景**为单位，
不以组件引入为单位。

## 2. 阶段总览

| 阶段 | 解决的问题 | 主要产出 | 退出条件 |
|---|---|---|---|
| Phase 0 基线和设计（已完成） | 方向不清、环境不一致、AI 无统一上下文 | 仓库、设计文档、WSL/CLion、CMake/CI、登录切片 | 文档确认，骨架可构建，登录链路通过 |
| Phase 1 最小业务闭环（已完成） | 单点功能无法证明系统可用 | Match、Room、SSE 推送、Vue 演示、最小对战 | 双浏览器完成匹配、进房和对战 |
| Phase 2 持久化和恢复 | 重启后状态丢失、重连不可靠 | Redis/MySQL 快照、Session 恢复、对局结果幂等写入 | 重启和断线后能恢复 |
| Phase 3 可观测性和容量基线 | 无法定位性能与错误来源 | Prometheus、Grafana、压测脚本、首份报告 | 指标可查，数据可复现 |
| Phase 4 故障注入与可靠性验证 | 设计上的容错能力从未被真实触发 | 故障注入脚本、恢复时间记录、优雅退出与排空 | 每个故障场景都有实测证据 |
| Phase 5 工程收口 | 缺少稳定性证据和可复现材料 | Runbook、演示脚本、验证报告 | 能稳定演示并解释所有取舍 |

总周期约 14 至 16 周。按每天 2 至 3 小时计算，总投入约 300 至 350 小时。

### 已取消的阶段（不实现）

原 Phase 4（多实例和故障治理，引入 etcd）与原 Phase 5（事件闭环和回放，引入
Kafka 与 Settlement Worker）**已由 [ADR-0003](adr/0003-scope-reduction.md) 取消**。

同批列入非目标的还有：Kubernetes、独立 Player/State 服务、独立 Settlement 服务、
排行榜、匹配分差放宽。这些**不是"延后"，是当前不做**；要恢复必须先撤销 ADR-0003。

技术栈及验收标准产生不同理解。

### 范围

- 配置 CLion WSL Toolchain、CMake 和 Ninja。

### 非范围

## 4. Phase 1：最小业务闭环（已完成，2026-10-02）

### 触发原因

只有登录不足以证明后端可用。需要打通“匹配 -> 房间 -> 对战 -> 结算”的最小
用户价值链路。

### 范围

- 定义数据模型和数据库迁移。（已完成 TASK-006）
- 实现 Match Service。（已完成 TASK-007）
- 实现 Room/Battle Service。
- 实现 Gateway 的 SSE 推送路由（见 ADR-0004）。
- 实现 Vue 登录页、大厅、对战页和结算结果。
- 两个浏览器或机器人完成最小对战。
- 对局结束时由 Room/Battle 同步幂等写入 `match_results`。

### 非范围

- 不实现排行榜、领域事件和异步结算。
- 不实现 Player/State 与 Settlement 服务。

### 退出标准

- 两个客户端可以登录、匹配、进入同一房间并完成对局。
- 正常路径和主要异常路径有测试。
- 页面能显示连接、匹配和房间状态。
- 能用一条命令启动集成环境。

## 5. Phase 2：持久化和恢复

### 触发原因

Phase 1 允许使用内存状态，但进程重启会丢失会话和房间。真实服务必须定义恢复边界。

### 范围

- MySQL 保存玩家、房间记录和对局结果。
- Redis 保存会话、缓存和短期状态。
- 房间定期保存快照。
- 登录和匹配请求使用已有的幂等键；对局结果使用 `match_id` 作为幂等业务键。
- 进程重启后恢复关键状态。
- 断线重连恢复房间位置和缺失状态（宽限期语义在 Phase 1 已设计，此处落地）。

### 非范围

- 不实现跨节点迁移，不做多实例。
- 不引入任何消息队列。

### 退出标准

- 服务重启后已确认的玩家和对局结果不丢失。
- 宽限期内重连可以恢复房间。
- 重复写入不产生重复对局结果。
- 恢复时间有测量结果和限制说明。

## 6. Phase 3：可观测性和容量基线

### 触发原因

如果没有指标和固定环境，任何性能判断都只是主观感受，也无法验证。

### 范围

- 结构化日志和请求 ID。
- 连接数、QPS、延迟直方图、错误率和房间数指标。
- Prometheus 采集和 Grafana 面板。
- 关键同步路径加入链路追踪。
- 建立 1、10、50、100、500、1000 连接档位。
- 只记录瓶颈，不立即优化。

### 退出标准

- 任一错误可以定位到服务、请求、会话或房间。
- 压测脚本、环境、版本和原始结果可复现。
- 至少识别一个明确瓶颈，并决定暂不优化或进入下一阶段。

## 7. Phase 4：故障注入与可靠性验证

### 触发原因

前三个阶段建立的是"设计上应该能容错"。但设计上的容错如果不被真实触发，
就只是假设。本阶段的目的是把每一个故障场景变成**有实测记录的事实**。

### 范围

- **依赖不可用**：Redis 停机、MySQL 停机与恢复（Phase 1 已有部分证据，
  此处补全并固化脚本）。
- **进程崩溃与恢复**：`kill -9` 业务进程，验证快照恢复边界与状态偏差。
- **断线重连**：宽限期内的会话与房间位置恢复；宽限期到期后的资源回收。
- **连接风暴**：瞬时大量连接建立，验证限流与拒绝行为，已有连接不受影响。
- **优雅退出与排空**：SIGTERM 后停止接收新房间、等待活跃对局结束、超时补偿。
- **长稳运行**：持续连接、断连、重连，观察内存与 FD 是否稳定。

### 非范围

- 不引入 etcd、Kafka、多实例或容器编排。
- 不做跨节点故障迁移（没有多节点）。
- 不为通过测试而放宽既有验收标准。

### 退出条件

- 每个故障场景都有可重复执行的注入脚本。
- 每个场景都有实测的检测时间、恢复时间和数据丢失边界。
- 已知无法恢复的场景被明确记录，而不是被隐藏。
- 恢复过程不产生假成功、不静默丢数据。

## 8. Phase 5：工程收口

### 范围

- 修复稳定性问题，不新增业务范围。
- 完成最终容量报告和故障注入结果汇总。
- 完整 README、架构图、ADR 和 Runbook。
- 演示脚本和故障恢复脚本。

### 退出标准

- 一条命令启动系统。
- 15 分钟内完成完整演示。
- 任一性能或可靠性数字均能回溯原始记录。
- 能解释每个技术选择的替代方案和代价，**包括为什么不做 Kafka、etcd 和多实例**。

## 9. 迭代变更规则

- 延后阶段不需要道歉，但必须说明当前证据不足。
- 提前阶段必须说明已有触发证据和新增风险。
- 新增范围必须评估是否影响当前退出标准。
- 删除或降低验收标准必须写 ADR，并记录原因。
- 不接受“已经做了很多，所以加一个版本号”的迭代方式。
- **被 ADR 列为非目标的组件，不以"现在满足准入条件"为由直接实现**；
  必须先撤销对应 ADR。

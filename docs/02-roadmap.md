# 迭代路线图

> 状态：已确认（2026-09-14）

## 1. 迭代原则

项目按“正确 -> 可恢复 -> 可观测 -> 可扩展 -> 可优化”推进。

每一阶段必须回答：

1. 当前存在什么问题？
2. 为什么现在必须解决？
3. 不解决会影响哪个功能、指标或故障场景？
4. 最小改动是什么？
5. 如何证明问题被解决？
6. 哪些能力明确留到后续，不提前实现？

版本号只记录已经交付的结果，不驱动开发。压测只用于建立基线和发现瓶颈，
不是自动进入优化的理由。

总周期约 12 至 14 周。按每天 2 至 3 小时计算，总投入约 300 至 350 小时。

## 3. Phase 0：基线和设计

### 触发原因

当前只有方向和零散讨论。若没有统一文档，Claude、豆包、DeepSeek 和项目所有者会
对项目范围、技术栈及验收标准产生不同理解。

### 范围

- 创建 GitHub 仓库和本地 WSL 项目。
- 配置 CLion WSL Toolchain、CMake 和 Ninja。
- 完成项目章程、架构、路线图、AI 协作和任务文档。
- 建立最小 C++ 工程、CI、格式和测试框架。
- 完成 Gateway 健康检查。
- 完成登录到 Redis Session 的第一个垂直切片。

### 非范围

- 不实现匹配和房间。
- 不引入 Kafka、etcd 和多节点。
- 不实现复杂前端。

### 退出标准

- 文档经过项目所有者确认。
- WSL 中能构建、测试和运行 Gateway。
- CI 能完成构建和测试。
- 登录链路有单元测试和集成测试。

## 4. Phase 1：最小业务闭环

### 触发原因

只有登录不足以证明后端可用。需要打通“匹配 -> 房间 -> 对战 -> 结算”的最小
用户价值链路。

### 范围

- 定义数据模型和数据库迁移。
- 实现 Match Service。
- 实现 Room/Battle Service。
- 实现 Gateway WebSocket 路由。
- 实现 Vue 登录页、大厅、对战页和结算结果。
- 两个浏览器或机器人完成最小对战。

### 退出标准

- 两个客户端可以登录、匹配、进入同一房间并完成对局。
- 正常路径和主要异常路径有测试。
- 页面能显示连接、匹配和房间状态。
- 能用一条命令启动集成环境。

## 5. Phase 2：持久化和恢复

### 触发原因

Phase 1 允许使用内存状态，但进程重启会丢失会话和房间。真实服务必须定义恢复边界。

### 范围

- MySQL 保存玩家、战绩和必要房间记录。
- Redis 保存会话、缓存和短期状态。
- 房间定期保存快照。
- 登录和结算请求加入幂等键。
- 进程重启后恢复关键状态。
- 断线重连恢复房间位置和缺失状态。

### 退出标准

- 服务重启后已确认的玩家和战绩不丢失。
- 宽限期内重连可以恢复房间。
- 重复结算不产生重复战绩。
- 恢复时间有测量结果和限制说明。

## 6. Phase 3：可观测性和容量基线

### 触发原因

如果没有指标和固定环境，任何性能判断都只是主观感受，也无法验证。

### 范围

- 结构化日志和请求 ID。
- 连接数、QPS、延迟直方图、错误率和房间数指标。
- Prometheus 采集和 Grafana 面板。
- 关键同步路径加入链路追踪。
- 建立 1、10、50、100、500、1000 连接档位。
- 只记录瓶颈，不立即优化。

### 退出标准

- 任一错误可以定位到服务、请求、会话或房间。
- 压测脚本、环境、版本和原始结果可复现。
- 至少识别一个明确瓶颈，并决定暂不优化或进入下一阶段。

## 7. Phase 4：多实例和故障治理

### 触发原因

只有压测证明单节点存在容量限制，或故障测试证明需要服务发现和迁移，才进入本阶段。

### 范围

- Gateway 和 Match 至少运行两个实例。
- etcd 注册、发现、健康检查和租约。
- 房间分配考虑节点负载和故障失败。
- 服务优雅退出与请求排空。
- 节点故障检测、降级和恢复测试。

### 退出标准

- 关闭任一 Gateway 或 Match 实例不会导致系统完全不可用。
- 故障检测和恢复时间有数据。
- 不会静默丢失已确认的匹配或结算。

## 8. Phase 5：事件闭环和回放

### 触发原因

当结算需要异步化，或需要回放、统计、审计时，同步调用和普通日志不再合适。

### 范围

- Kafka Topic 和事件 Schema。
- Room 发布领域事件。
- Settlement Worker 消费和幂等处理。
- 消费位点、重试、死信和积压监控。
- 对局事件回放。

### 退出标准

- 重复消费不会重复结算。
- 服务重启后可以从已提交位点继续。
- Kafka 积压不影响进行中的对局。
- 可以在演示页查看一场对局的事件回放。

## 9. Phase 6：工程收口

### 范围

- 修复稳定性问题，不新增业务范围。
- 完成故障注入、长稳测试和最终容量报告。
- 完整 README、架构图、ADR 和 Runbook。
- 演示脚本和故障恢复脚本。
- 对外描述只引用可复现证据。

### 退出标准

- 一条命令启动系统。
- 15 分钟内完成完整演示。
- 任一性能或可靠性数字均能回溯原始记录。
- 能解释每个技术选择的替代方案和代价。

## 11. 迭代变更规则

- 延后阶段不需要道歉，但必须说明当前证据不足。
- 提前阶段必须说明已有触发证据和新增风险。
- 新增范围必须评估是否影响当前退出标准。
- 删除或降低验收标准必须写 ADR，并记录原因。
- 不接受“已经做了很多，所以加一个版本号”的迭代方式。

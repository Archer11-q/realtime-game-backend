# 项目章程

> 状态：已确认（2026-09-14），**2026-10-02 按 [ADR-0003](adr/0003-scope-reduction.md)
> 裁剪范围与非目标。**

## 1. 项目名称

`Realtime Game Backend`，面向小型实时对战产品的游戏服务端参考实现。

## 2. 项目背景

面向小型实时对战产品的后端，需要同时处理连接、匹配、房间状态、断线重连、
数据持久化、对局结果写入和运行故障。单机原型通常可以完成基础流程，但很难覆盖
恢复边界、故障降级和可观测性。

本项目**不做多节点与服务治理**（见第 7 节非目标），深度优先于广度。

本项目从实际业务链路出发，回答以下工程问题：

- 有状态服务如何可靠地部署、恢复和排障。
- 同步接口和持久化之间如何划分职责。
- 重复请求、进程崩溃和依赖不可用时如何保持正确性。

## 3. 目标用户

### 直接使用者

- 项目开发者：学习、开发和验证 C++ 服务端工程能力。
- 技术评审者：通过代码、文档、监控和现场演示判断系统能力。
- 后续 AI 开发者：通过仓库文档理解方向并继续迭代。

### 模拟业务用户

- 小型实时对战游戏的玩家。
- 自动化机器人客户端。
- 负责观察运行状态和故障恢复的运维人员。

## 4. 需要解决的问题

| 问题 | 当前表现 | 本项目解决方式 |
|---|---|---|
| 单机容量有限 | 连接、匹配和房间集中在一个进程 | 按证据拆出 Gateway / Match / Room-Battle 三个服务；**不做多实例**，见 ADR-0003 |
| 状态易丢失 | 进程重启后会话和房间丢失 | MySQL 持久化关键数据，Redis 保存短期状态，定义快照与恢复 |
| 请求重复 | 重试可能重复入队或结算 | 幂等键、状态机和重复请求测试 |
| 服务边界混乱 | 网关、匹配、房间和结算相互访问数据 | 明确职责和数据所有权 |
| 故障不可恢复 | 进程崩溃后缺少恢复边界 | 房间快照与恢复；**不引入 etcd、租约或节点迁移**，见 ADR-0003 |
| 无法证明性能 | 只有单次测试或主观判断 | 固定环境、可复现脚本、指标和容量报告 |
| 难以排障 | 只有分散日志 | 结构化日志、指标、链路和 Grafana 面板 |
| 项目展示抽象 | 只能通过代码推断系统行为 | 提供浏览器演示、机器人和故障注入 |

## 5. 项目目标

### 功能目标

- 玩家可以登录、匹配、进入房间并完成一场最小实时对战。
- 浏览器断线后，可以在宽限期内恢复会话和房间位置。
- 对局结束后可以查询对局结果，且重复写入不产生重复记录。
- 房间、匹配和结算的重复请求具备可验证的幂等行为。

### 工程目标

- 在 WSL2 + CLion 中完成 Linux C++ 开发和调试。
- 使用 brpc + Protobuf 定义清晰的内部服务契约。
- 使用 Redis/MySQL 保存不同类型的状态。
- 通过 Docker Compose 一条命令启动本地集成环境。
- 通过 GitHub Actions 执行构建、测试和静态检查。
- 使用 Prometheus、Grafana 和结构化日志建立可观测性。
- 用压测和故障注入证明性能及恢复能力，而不是只展示实现。

### 展示与验证目标

- 能连续讲解项目架构和业务链路 10 至 15 分钟。
- 能解释设计取舍、替代方案、故障模型和性能数据。
- 能通过浏览器、机器人、监控面板和故障注入验证系统行为。
- 所有对外描述都必须能够追溯到代码、测试或原始运行记录。

## 6. 成功标准

初始验收目标如下。数字可以在基线建立后通过 ADR 调整，但不能为了通过测试而
临时降低标准。

| 维度 | 初始目标 |
|---|---|
| 并发连接 | 至少 1000 个模拟连接 |
| 活跃房间 | 至少 100 个 |
| 控制面延迟 | p99 不高于 200ms |
| 游戏帧广播 | p99 不高于 100ms |
| 错误率 | 低于 0.1% |
| 进程恢复 | 10 秒内恢复关键会话和房间 |
| 依赖故障 | Redis/MySQL 不可用时返回明确错误、不写假成功，恢复后无需重启 |
| 对局结果幂等 | 同一 `match_id` 重复写入不产生重复记录 |
| 工程质量 | 单测、集成测试、E2E、ASan、TSan 按阶段通过 |

## 7. 非目标

- 不实现完整商业游戏，不做复杂玩法、美术和支付。
- 不追求完整账号平台、社交系统和大规模运营后台。
- 不重新实现通用 RPC 框架。
- 不自研数据库、消息队列或服务发现系统。
- 不以微服务数量、代码行数和版本号衡量成果。
- 不编造用户量、QPS 或线上经历。

### 已确认的非目标（2026-10-02，见 ADR-0003）

以下内容**当前不做，且不是"延后"**。不得为其创建目录、proto、源文件、测试、
Compose 服务或环境变量：

- Kafka 及任何消息队列、领域事件、事件回放、异步结算 Worker。
- etcd 及任何服务注册、发现、租约机制。
- 多实例部署与水平扩展。
- Kubernetes / k3s / 容器编排。
- 独立的 Player/State 服务与独立的 Settlement 服务。
- 排行榜。
- 匹配分差放宽 / MMR / 评分体系。

要恢复其中任何一项，必须先从"替代关系"角度撤销或修改 ADR-0003。

## 8. 约束

- 主开发环境固定为 WSL2 Ubuntu 26.04 LTS + CLion。
- 当前已验证工具链为 GCC 15.2、CMake 4.2.3、Ninja 1.13.2、Git 2.53.0、
  Protobuf 3.21.12 和 vcpkg 2026-07-27。
- 正式源码目录固定为 `~/workspace/realtime-game-backend`，位于 WSL Linux
  文件系统，而不是 `/mnt/d`。
- 服务间通信固定为 brpc + Protobuf。
- 浏览器通信固定为 HTTP + WebSocket。
- 业务实现采用 C++20，演示前端采用 Vue 3 + TypeScript。
- 外部依赖版本需要固定并记录。
- 每个阶段都必须可构建、可测试、可回退。
- AI 不拥有最终决策权，项目所有者负责确认和合并。

## 9. 主要风险

| 风险 | 影响 | 缓解方式 |
|---|---|---|
| 范围过大 | 长期停留在半成品 | 垂直切片、单任务、最小闭环 |
| 技术组件堆叠 | 复杂度高但无真实价值 | 每个组件必须有触发条件和 ADR |
| AI 代码不一致 | 风格冲突、重复实现 | Claude 是唯一代码负责人，用户统一验收 |
| 过早分布式 | 调试困难、进度失控 | 服务只拆三个，且不做多实例（ADR-0003） |
| 压测数据不可复现 | 无法证明性能和容量结论 | 固定环境、脚本、原始记录和版本 |
| 文档与代码不一致 | 后续 AI 判断错误 | 变更时同步更新，发现冲突立即停止 |

## 10. 项目边界决定

本项目必须始终满足以下一句话：

> 它是一个可以真实运行、观察、压测和恢复的实时对战后端系统，而不是一组演示
> 技术名词的代码目录。

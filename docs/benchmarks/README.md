## 1. 结论摘要（先看这里）

1. **1000 并发连接（=500 个并发对局）可以跑起来，但已经越过了第一处瓶颈。**
   在 1000 档位上，"进入匹配"（`POST /api/v1/matches`）的 P95 达到 **956 ms**、
   P99 **991 ms**（100 档位时分别是 88 ms / 99 ms）。
2. **瓶颈位置：Match 的匹配队列快照写入在请求路径上，并被一把全局锁串行化。**
   `MatchQueue::PersistSnapshot()` 用 `snapshot_order_mutex_` 把"取快照 + 写 Redis"
   整体串起来，因此每一次"状态有变化的入队/轮询"都要排在前面那次 Redis 写之后。
   1000 个客户端同时入队时，这一次写入的排队时间就是 565 ms 的 P50。
3. **这不是新发现，而是 Backlog 里那条已知限制的量化确认**
   （`docs/TASKS.md` 的 Backlog：「把匹配队列的快照写入移出请求路径」，TASK-015 时期
   记录，当时因为"没有证据"被推迟）。本报告给出了证据。
4. **其他端点没有成为瓶颈**：`rooms/input`（攻击）P95 仅 9.4 ms、
   `rooms/join` P95 85 ms、`rooms/state` 不参与压测路径。
   **房间推进与快照写入本身没有饱和**（500 档位每秒推进 729 帧、写 301 次快照，
   服务端延迟仍在毫秒级）。
5. **内存不是约束**：1000 档位下三个服务 RSS 合计约 211 MB
   （Gateway 77.6 MB / Match 63.2 MB / Room 61.1 MB），线程数恒定 21/20/21。

## 2. 测试环境（可复现的前提）

完整快照见 `docs/benchmarks/raw/20261004-140614/logs/env.txt`。要点：

| 项 | 值 |
|---|---|
| 机器 | WSL2 Ubuntu 26.04，16 vCPU，内存 11 GiB（Docker Desktop 上限相同） |
| 服务 | Gateway / Match / Room，`brpc-debug` 预设（**Debug，未开优化**） |
| 依赖 | Redis 8.0 与 MySQL 8.4，Docker Compose 起在同一台机器 |
| 压测端 | `bench/loadgen.py`，Python 3.14 + asyncio，与三个服务**同机** |
| 观测 | Prometheus 5 秒抓取；服务端 `/metrics` 另在每档结束时直接抓一份 |
| 端口 | 8080 / 8082 / 8083（脚本强制，不换端口，理由见 `scripts/bench.sh` 头部） |

**三条必须说清的前提**（否则数字会被误读）：

1. **压测端与被测服务同机**，两者争抢同一份 CPU 与内存。因此这里测到的是
   *单机上限*，不是服务端能力的上限。
2. **Debug 构建**。绝对延迟会显著高于 Release；本报告用于**横向比较档位**与
   **定位瓶颈**，不用于宣称绝对性能。
3. **N 个连接 = N/2 个并发房间**。Gateway 的推送线程对每个"有订阅者的房间"
   每 100 ms 轮询一次 Room，因此连接数上去后 **RPC 量按房间数放大**：
   500 档位实测 597 次/秒，1000 档位 1712 次/秒。

## 3. 压测方法

```bash
bash scripts/bench.sh                                  # 全部 6 档
bash scripts/bench.sh --level 100                       # 单档可独立运行
bash scripts/bench.sh --levels 100,500 --duration 30    # 指定档位与时长
```

- **档位**：1 / 10 / 50 / 100 / 500 / 1000 连接，每档 **60 秒**。
- **负载模型**：每个虚拟玩家走完整链路——登录 → 入队 → 轮询到配对 → 进房 →
  建 SSE 长连接 → 每 2 秒提交一次攻击。每 2 秒意味着单局约 20 秒（每次扣 10 血、
  满血 100）。
- **每档重启服务并清状态**：档位之间不共享进程内存、Redis 快照与 `rooms` 表。
  不清状态会复用到上一档的房间或匹配结果（TASK-021 的 `verify-trace.sh`
  踩过同一坑），档位之间就不可比了。
- **每档为每个机器人准备独立玩家身份**（`bench-00000` … `bench-00999`）。
  这一点是必须的，理由见第 6 节——第一轮没有这么做，得到的数字**全是夹具假象**。
- **退出时会清理自己造的状态**：删除 `bench-*` 账号、清空 `rooms` 与
  `match_results`、清掉 Redis 的 `dev:*`。**这一点是实测踩出来的**：
  第一版压测跑完后开发库里多了 1000 个账号与 1181 行对局结果，于是
  `scripts/verify-login.sh` 的"players 行数为 4"断言直接失败，
  同一轮 `verify-all.sh` 里 `verify-room` / `verify-stream` 也失败
  （Room 启动时要恢复上一轮遗留的房间，ticker 被快照写入拖住，新对局推进不动）。
  失败信息（"对局打不完"）与真实原因（上一轮的残留状态）毫无关系——
  这与本任务第 6 节记的账号池问题是同一类：**夹具污染环境，然后伪装成系统缺陷**。
  需要保留现场排查时用 `--keep`。

### 3.1 为什么每档用独立账号（一次真实的方法学失败）

第一版压测复用了种子账号 `alice/bob/dave`（内置启用身份只有 3 个），于是 1000 个
机器人只产生 **3 个 `player_id`**，直接导致：

- 同一玩家的重复入队被幂等判为 `kAlreadyQueued`（实测 997/1000 次），
  **队列里根本没有 1000 个人**；
- 同一玩家的重复进房是**幂等成功**（`BattleRoom::Join` 在 `player->connected` 时
  直接返回 `kOk`），于是"重复加入同一个已结束房间"被计成正常对局；
- 最终得到 `room_created=1` 却 `room_joined=667` 这种自相矛盾的数字——
  667 次 join 不可能挤进一个两人房间。

**结论：那些数字既不是容量上限也不是缺陷证据，只是夹具的假象。** 修正方式是为每个
机器人准备独立身份（Gateway 侧新增 `-enable_bench_accounts`，默认关闭，
只识认严格的 `bench-<5 位数字>`）。修正前后同一档位的对比：

| 指标（1000 连接） | 复用 3 个账号 | 每机器人独立身份 |
|---|---|---|
| 成功配对 | 667 | **1000** |
| 服务端建房间数 | 1 | **2979**（含重试） |
| 成功攻击 | 694 | **25218** |
| `rooms/join` 503 | 640 | **0** |

## 5. 瓶颈结论

### 瓶颈：Match 的队列快照写入在请求路径上，并被一把全局锁串行化

**判定依据（全部可在原始数据里复核）**：

1. **只有"会改变队列状态"的端点在 500/1000 档位劣化**，而登录、攻击、进房都没有。
   这与"某个共享写入路径饱和"的表现一致，而不是"CPU 打满"或"网络受限"。
2. **机制在代码里可指认**：`MatchQueue::PersistSnapshot()` 先用
   `snapshot_order_mutex_` 把"取快照 + 写 Redis"整体锁住，再在内部短暂地取队列锁
   （`src/match/match_queue.cpp`）。因此 Redis 写的耗时被**串行叠加**到每一个
   状态变化的请求上；1000 个客户端同时入队时，第 N 个请求要等前面 N-1 次写入。
3. **`GetStatus` 走同一条路径**：轮询触发的超时清算（`SweepLocked`）也会
   `PersistSnapshot()`，这解释了为什么"只是查状态"的端点 P95 会到 859 ms。
4. **量的边界**：100 档位（快照里最多 100 条）P95 88 ms 仍可接受；
   500 档位（最多 500 条）P95 842 ms 已越界。说明成本随**队列长度**增长，
   而不是随并发数增长——这正是"整份重写"策略的固有代价
   （TASK-015 决策 1：用 `MULTI/DEL/REPUSH` 原子替换整个 LIST）。
5. **对照组**：500 → 1000 档位时 Gateway 的 HTTP 请求速率反而从 762.9/秒降到
   663.8/秒，而匹配相关端点的延迟涨了近一倍。**"速率下降 + 延迟上升"是排队饱和的
   典型特征**，而不是容量耗尽后的雪崩。

**这不是新问题**，而是 Backlog 里已记录的限制的量化确认：

> 把匹配队列的快照写入移出请求路径（TASK-015 期间记录）……
> 彻底解决需要独立写入线程或定时器（引入并发），**先要有证据**。

### 本报告没有把以下现象当瓶颈（列出以说明取舍）

- **`create_room_failed` 2479 次（1000 档）**：Match 分配房间时的传输失败。
  但配对最终 100% 成功（重试机制 TASK-007 的惰性重试生效），
  且 Room 侧延迟仍在毫秒级——因此它是**次生现象**（Match 在等快照锁时超时），
  不是独立瓶颈。
- **`/api/v1/stream` P95 215 ms**：偏高但未突破 250 ms，且它只在建流时发生一次，
  不影响对局过程。记为**第二位待观察项**。
- **登录 P95 24 ms**：与档位无关（100/500/1000 三档几乎相同），说明这一路径已经
  饱和在自己的下界上，不是瓶颈。

## 6. 未测与已知限制

1. **Release 构建未测**。全部数字来自 `brpc-debug`。要得到可用于容量规划的数字
   必须重跑 `release` 预设——那属于下一阶段的事，本报告不作推测。
2. **压测端与服务同机**，因此测到的是单机上限；真实部署下客户端在别的机器上。
3. **对局推进的稳态窗口有限**。单局约 20 秒、每档 60 秒，因此每档包含"开场配对"
   与"打完重入队"两种相位。**重入队受 120 秒结果保留期限制**（见下），
   所以本报告没有测"长期稳态吞吐"。
4. **120 秒结果保留期**（`kDefaultResultTtlMs`）意味着一个玩家打完一局后
   120 秒内无法再次配对。这是设计行为（保护"配对成功但客户端还没领取"的结果），
   但它在高并发下会限制整体对局周转率。本报告**没有**把它当瓶颈，
   因为它的影响需要更长的运行窗口才能与快照锁分开。
5. **未做故障注入**（Redis/MySQL 停机、进程崩溃）——那是 Phase 4 的范围。
6. **Prometheus 侧的 P95 取的是聚合值**（直方图带 `path` 标签，但 `rate[1m]` 在
   60 秒窗口内样本太少）。本报告的分位数一律从端点原始文本按 `path` 分组现算，
   与 Grafana 面板口径一致（同一个直方图）但**不依赖 Prometheus 侧的窗口**。
7. **`room_frames_advanced_total` 是累计值**，本报告把它除以墙钟时长得到
   "帧推进/秒"。它衡量的是**所有房间的帧号之和**，因此 1000 档位（500 房间 ×
   10 Hz 上限 ≈ 5000 帧/秒）实测 471 帧/秒，反映的是"多数房间在 60 秒内没有
   打满 600 帧"，而不是帧率不足。

## 7. 后续决定

**决定：本阶段（Phase 3）不优化，把瓶颈结论作为 Phase 4 的输入。**

理由：

1. **Phase 3 的纪律是"只记录瓶颈，不立即优化"**（`docs/02-roadmap.md` 第 6 节）。
   本报告已经兑现了退出标准要求的那一条：**识别至少一个明确瓶颈并作出决定**。
2. **优化需要独立写入线程**（把 Redis 写从请求路径摘出去），这会给 Match 引入
   新的并发路径。按 `CLAUDE.md` 第 6 条，这类改动应该由**故障注入与容量证据**
   驱动；现在证据已经拿到，但它更自然的落点是 Phase 4（故障注入）之后，
   因为那时才知道"Redis 挂起"与"队列很长"哪一种更该被优先处理。
3. **不影响当前 SLO 的可接受档位**：500 档位以下，只有入队在极端并发下越过
   P95 100 ms；1000 档位才是明确越界。项目当前的目标场景（演示、故障注入）
   在 500 以下。

**建议的下一步（写入 Backlog，不在本任务实现）**：

- **把 Backlog 那条"把匹配队列快照写入移出请求路径"升级为有证据的任务**，
  并补上这次的量化目标：**500 档位入队 P95 < 100 ms**（当前 842 ms）。
- 顺带评估同一条路径上的第二个成本项：**整份重写**策略在队列很长时的序列化开销
  （1000 档位每份快照 ~1000 条）。若改成增量更新需要自己维护顺序，
  收益需要与"独立写入线程"一起评估。
- 把 **`rooms/join` / `stream` 的 P95（85 ms / 216 ms）** 记为第二位观察项，
  在 Release 构建下复测后再判断是否需要动作。

### 1. 结论摘要

1. **内存与线程是稳定的**：三个服务的线程数全程不变（21 / 20 / 21）；
   RSS 在窗口内都出现过回落，增长率分别为 Gateway +5.8 MB、Room +3.5 MB、
   Match +0.8 MB（30 分钟），**没有证据表明内存泄漏**。
2. **订阅数与 Gateway 的 fd 数不稳定，而且在 30 分钟里单调增长**：
   SSE 连接数 50 → 160、Gateway fd 114 → 254。客户端全部离开后的 60 秒静默期里，
   订阅数仍停在 **150**（此时客户端只剩 0 条）——**订阅没有被回收**。
3. 这正是 TASK-027 任务单预判的失败场景："SSE 连接数在断连后不下降
   （订阅未清理）"。按任务单的非范围，本轮**只给证据、不修**。

### 3. 压载本身是有效的（否则上面的数字没有意义）

`soak.json`：29 个断连周期、累计主动断开 **290** 条 SSE、重连 **290** 次、
`streams_opened=340`、结束时仍连着 **50** 条、窗口内推送事件 **183742** 条。
也就是说"断连/重连"这条链路真的被压了 290 次。

### 4. 一个反例：单条订阅可以被正常回收

最小复现（1 个房间 / 1 条订阅 / 客户端干净关闭）**不能**复现：
订阅数在 5 秒内从 1 回落到 0。因此触发条件是"**重复断连 + 立即重订阅**"，
不是"客户端关闭后服务端永远不回收"。根因未定位，下一步要做的是区分
**服务端订阅未回收**与**压载端 socket 泄漏**（后者的话服务端保留订阅是正确的）：
压载中同时统计客户端进程持有的 socket 数与服务端每个订阅距上次写入的时间。

### 7. 数据缺口与口径说明（如实记录）

1. **四类故障注入（TASK-023/024/025/026）没有原始数据归档**：数字只存在于任务单与
   devlog 的实施记录里。`docs/benchmarks/raw/` 下的 `20261005-*` 目录属于容量/长稳/
   TASK-035 实验，**不要**把它们当成故障注入的归档。
2. **TASK-028 一节的既有表格是混源的**（中间轮与交付轮混排），按规则 3 未改动，
   引用时须注明（见 §3）。
3. **TASK-035 文字口径里的「142 ~ 240 ms」「6 ~ 11 ms」是 prose 合成区间**：逐轮原始值里
   enqueue RPC 段最小 141、对端 handler 最大 81；本次 V3 复跑（239 / 94）也在该区间内。
4. **「80% 空闲 / 运行队列 1.3」（TASK-035 第 2 步）只有 devlog 文字，无 raw 归档**
   （`vmstat` 输出在 `.run/`，不入库）。
5. **SLO 的权威出处**：`docs/04-quality-and-observability.md` 第 5 节**没有**列出
   「p95 < 100 ms、p99 < 250 ms」的数值；数值分散在 `docs/TASKS.md`（直方图桶边界取
   SLO 线 50/100/250 ms 等处）与 `docs/devlog.md`。建议 TASK-034 把 SLO 数值写回
   `docs/04-quality-and-observability.md` 第 5 节，统一权威出处。
6. **`scripts/bench.sh` 的墙上时长**：本机 coreutils 9.x 的 `date +%s%3N` 不是真实毫秒；
   首尾同源相减因此内部一致，既有数字不受影响；新增脚本一律用 `EPOCHREALTIME`。

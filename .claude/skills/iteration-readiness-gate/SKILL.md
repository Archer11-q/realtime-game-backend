# 迭代前就绪性评估（Iteration Readiness Gate）

## 用途

在一个"文档即真相"的仓库里，"我现在能开始写代码了吗" 从来不是一个可以拍脑袋回答的问题。
本 Skill 把这个问题变成一条可复现的检查流水线，输出一份**阻塞清单**而不是一堆猜测。

**触发场景**

- 项目所有者说："读文档，指出我还需要完成什么，你才能开始迭代。"
- 新会话接手一个已有 `docs/` 和 `CLAUDE.md` 的仓库，准备动第一个任务。
- 一个迭代刚结束，准备进入下一个阶段，需要重新确认准入条件。
- 任何人（包括你自己）倾向于"先写点代码再说"时。

**不适用**：已经确认就绪、正在执行具体任务的过程中。那是执行阶段，不是评估阶段。

## 三条核心原则

1. **文档声称 ≠ 实测事实。** 文档写 Ubuntu 24.04，实测可能就是 26.04；文档说"已配置 CI"，`.github/` 可能根本不存在。
   两者冲突时**不要自行选一个**——记录冲突，交项目所有者裁决。这是本流程产出价值最高的部分。
2. **证据优先于推断。** 环境能力用命令实测，不用"应该装了"。仓库状态用文件系统实测，不用"文档里有目录就等于有代码"。
3. **评估阶段不改任何东西。** 不改代码、不改文档状态、不装依赖、不建 git 仓库。评估的唯一产物是**报告 + 待确认决策**。

## 执行步骤

### S1 · 按序读取治理文档

严格按仓库自己规定的阅读顺序（通常在 `docs/README.md` 里）。典型顺序：

```
CLAUDE.md（根，最高优先级规则）
  → docs/README.md（索引与阅读顺序）
  → 项目章程 / 架构 / 路线图
  → 开发流程 / 质量与可观测性 / 接口与数据 / 运维
  → 开放决策与风险
  → 当前任务单（TASKS.md）
  → devlog（只记录已发生的事实）
  → docs/adr/ 下所有 ADR（注意每个 ADR 的"状态"字段）
```

读取时同时记录**每个文档自报的状态**（`草案 / 待确认 / 已确认`）和**ADR 的状态**（`提议 / 已接受`）。
这些状态本身就是阻塞项的证据。

### S2 · 盘点仓库真实状态

不要相信目录存在就等于实现了。逐类核对：

```bash
# 声明的目录里到底有没有真实文件，还是只有 .gitkeep
find api src include tests bench chaos web deploy migrations scripts -type f 2>/dev/null | head -60

# git 仓库是否真的存在（文档说"已建仓库"时尤其要验）
git status 2>&1 | head -5
git remote -v 2>&1 | head -5

# 被文档当作既定事实的文件是否真的在
ls .github/workflows 2>/dev/null || echo "NO CI"
ls -a | head -30
```

产出**三态分类**：`已实现` / `仅骨架（.gitkeep）` / `声明存在但实际缺失`。

### S3 · 实测环境能力

对文档里承诺的每一种工具、版本、服务，逐条实测。**缺失也要显式打印，不要静默跳过**：

```bash
# 在项目规定的开发环境里执行（多为 WSL2）
echo "=== 发行版 ==="; lsb_release -ds 2>/dev/null || grep -E '^PRETTY_NAME' /etc/os-release
echo "=== 工具链 ==="
for t in git cmake ninja g++ gcc clang-format clang-tidy vcpkg docker protoc pkg-config \
         redis-cli mysql; do
  if command -v "$t" >/dev/null 2>&1; then
    printf '%-14s OK  %s\n' "$t" "$(command -v "$t")"
  else
    printf '%-14s MISSING\n' "$t"
  fi
done
echo "=== 版本 ==="
git --version 2>/dev/null; cmake --version 2>/dev/null | head -1
g++ --version 2>/dev/null | head -1; protoc --version 2>/dev/null
echo "=== 关键依赖库 ==="
ls /usr/include/openssl/ssl.h /usr/include/gflags /usr/include/glog 2>/dev/null || echo "缺依赖头文件"
echo "=== 容器与服务 ==="; docker info --format '{{.ServerVersion}}' 2>&1 | head -2
echo "=== 资源 ==="; nproc; free -h | head -2
```

> Windows 主机上的 WSL 项目：以上用 `wsl -d <发行版> -- bash -lc "<脚本>"` 从 PowerShell 进入执行。
> 开发目录若在 `/mnt/d/...`（Windows 文件系统），**必须额外记录**——跨文件系统构建会拖慢文件监听、Docker 卷挂载和 CLion 索引，这本身常是一条阻塞项。

对照文档的"环境要求表"逐项打勾，形成**差距表**。注意版本**不兼容**比版本**缺失**更隐蔽：
CMake 4.x 对旧 vcpkg port、GCC 15 默认语言标准、Protobuf 与 RPC 框架的版本耦合，都要显式标出。

### S4 · 生成冲突清单

把 S1 的声称与 S2/S3 的实测对齐，输出**文档 vs 实测**差异表。冲突至少包括三类：

| 类型 | 例子 | 处理 |
|---|---|---|
| 版本/环境不符 | 文档写 24.04，实测 26.04 | 记冲突，交裁决：改文档 or 重建环境 |
| 状态虚高 | 文档说"已建仓库/已配 CI"，实际不存在 | 记冲突，不可当作已完成 |
| 依赖前置未满足 | 任务 A 依赖任务 B，但 B 未开始 | 进入 S5 依赖链分析 |

**严禁自行选择方案。** 规则原文通常是"发现文档与实现冲突，停止编码并先报告冲突"。

### S5 · 定位总闸门任务

读当前任务单，画出依赖链，找出**卡住最多下游的那个任务**：

```
TASK-000（确认文档）─┬→ TASK-001（仓库与环境）→ TASK-002（骨架与 CI）
                     │                                    ├→ TASK-003（依赖容器）
                     │                                    └→ TASK-004（服务基线）
                     └────────────────────────────────────┴→ TASK-005（垂直切片 / 里程碑）
```

同时对照**里程碑定义**（M0/M1…）判断"当前阶段真正的最小验收目标"是什么，
避免把后期任务（消息队列、服务发现、多节点）误当成当前阻塞项。

### S6 · 阻塞分级

把所有阻塞项归入三类，按"你是否必须亲自做"排序：

- **A 决策类** —— 只有项目所有者能拍板，且**不拍板就无法动手**。
  典型：文档总确认（闸门）、项目最终目录、核心方案选型（鉴权/同步模式）、ADR 批准。
- **B 环境类** —— 需要安装或配置，且需要授权决定"谁执行"。
  典型：包管理器初始化、依赖库编译、Docker 集成、SSH 密钥。
- **C 授权/信息类** —— 需要外部信息或权限。
  典型：远程仓库名与可见性、License、CI 平台、执行人分工。

**明确标注非阻塞项**同样重要：告诉项目所有者"这几条可以先不决定，不挡当前阶段"，
能防止范围膨胀。

### S7 · 输出报告并停止

按仓库 `CLAUDE.md` 规定的输出格式交付。默认格式：

```text
任务：
结论：完成 / 部分完成 / 阻塞
修改文件：
设计说明：
测试命令与结果：
性能或安全影响：
未解决问题：
建议的下一步：
```

要点：

- `修改文件` 写 **无**，并显式声明"未改任何文件、未执行安装命令"。
- `测试命令与结果` 贴**真实执行过的命令与真实输出**，不编造。
- 报告正文先给"我对项目的理解"（证明读懂了），再给实测差距表，最后给阻塞清单。
- 阻塞项用结构化提问工具收敛（一次 3–5 个高价值问题），每个选项写清**代价**。
- 提问后**停下等待**。不要因为对方沉默就替其决策，也不要在等待期间"顺手"开始编码。

## 硬性禁止

1. 评估阶段不写业务代码、不改文档状态（`草案` → `已确认` 必须由所有者确认后授权）。
2. 文档与实测冲突时不自行选择方案，先报告。
3. 不执行需要授权的安装/初始化命令。
4. 不编造测试结果、版本号、性能数字或项目规模。
5. 不把后期阶段的技术（消息队列、服务发现、编排系统）当作当前阻塞项。

## 反模式

| 反模式 | 后果 |
|---|---|
| 看到目录结构就认定"骨架已就绪" | 忽略"只有 `.gitkeep`"的事实 |
| 把文档的"已完成"当作已验证 | 状态虚高通过评估，任务带病开工 |
| 用"应该装了"代替实测 | 环境缺口在 CI 或构建时才爆炸 |
| 一次性抛出十几个问题 | 所有者不回复，评估实际上被搁置——**按阻塞强度排序，只问最关键的** |
| 评估完直接开始改代码 | 违反"用户确认前不动手"的纪律 |

## 出口判据

评估结束的标志不是"能开始了"，而是以下全部成立：

- 每个阻塞项都有归属（谁来做）和类型（决策/环境/授权）。
- 文档与实测的冲突已列明且未被擅自消化。
- 总闸门任务已被指出，且其下游影响已被说明。
- 报告已按仓库规定格式交付，并给出了可执行的下一步。

之后由项目所有者答复决策，再输出**具体任务单**（含范围、非范围、验收命令、回退方式）等二次确认——
那才是进入下一轮迭代的入口。
